## 「mutex lock failed」不是 flake，是 VideoRendererImpl 析构的 UAF（已定位，未修）

之前一直当作「顺序相关的老 flake」放过，错了。全量重跑约 **1/4 概率 abort**，
`ctest` 把每个 gtest case 拆成独立进程所以永远掩盖它。**取栈的正解**：`std::terminate`
触发 SIGABRT 时 macOS 会写 `~/Library/Logs/DiagnosticReports/*.ips`，里面是全线程栈，
**不用挂 lldb**——lldb 附加会改变时序，连跑 5 次都干净（heisenbug 被调试器掩盖）。

两份 `.ips` 栈完全一致：

    VideoRendererImpl::PumpDecoder()            (media/filters/video_renderer_impl.cc:343)
      → VideoFrameCompositor::refresh_pending()  ← 第 346 行，函数第一条语句
        → base::Lock::Acquire() → std::mutex::lock() → EINVAL → terminate
    线程：avbase-test-S3

根因：`PumpDecoder()` 用 `base::Unretained(this)` 重投到 S3（:361、:477），
而 `~VideoRendererImpl()`（:43）只 `sink_->Stop()`，注释断言「Render() 是唯一从别的
序列碰 compositor 的东西」——**假**：`PumpDecoder` 也碰，而且 `compositor_` 是按值成员。
队列里残留的 pump 任务在 `compositor_`（及其内部 Lock）销毁后执行 → 锁已毁 mutex。
`stopping_` 检查在 :347，排在 `refresh_pending()` **之后**，挡不住。缺陷来自
`9c9fe13`（文件初次加入），与本次三次提交无关；三笔只碰了 legacy/av_sync_controller。

修法方向（未实施，需单独一轮）：`base/memory/weak_ptr.h` 已存在 → `WeakPtrFactory` +
`weak_factory_.GetWeakPtr()` 投递；同时把 `refresh_pending()` 挪到 `stopping_` 判断之后。
`decoder_stream_.Read(... Unretained(this) ...)`（:360）是同一类隐患，要一起看。

顺手改正：`ffmpeg_video_decoder_base.h` 的 `OnEndOfStream` 注释原写「重复 EOS 是 no-op」，
与实现不符（`decoding_eos_` 是**只写字段**，全树无人读；重复 EOS 只是重发 flush 包，
两条路径都把 `AVERROR_EOF` 当「已排空」）。已改为如实描述。
