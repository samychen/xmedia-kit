## `PipelineImpl::SetTickClock` 是假注入点，删掉

只写不读的成员本身不稀奇，但这个**会误导**：它长得像"时钟注入入口"，而真正的路径是

```
deps_->tick_clock ─→ AvSyncController(master, tick_clock)   // 成员 wall_
                        └─→ Clock audio_/video_/external_ 的 wall_
                                └─→ NowTicks()      ← 唯一真正调用的地方
                    └─→ pipeline->SetTickClock(...)  // 存了没人读
```

所以**时钟注入一直是生效的**，`PipelineImpl` 那份纯属冗余；它要求的
"`|clock|` must outlive the pipeline"也没人兑现。

**为什么选删而不是接上**：`PipelineImpl` 内部**没有任何 `NowTicks()` 调用点**
（媒体时钟在 `media/filters/legacy/clock.cc`）。接上去只能凭空造一个消费者。
依据是 `docs/TODO §2` 的原则：条目要么有下游读取者，要么移除。

删了 5 处（声明/成员/实现/`player_impl_prepare.cc`/两个测试 fixture），
`SetClock()` 的注释写明它是**唯一**注入点以及为什么旁边不该再长一个。

**方法论**：判断"只写字段该删还是该接"，别看字段名，看**它所在类有没有那个时钟的
消费点**。没有 → 删；有 → 接，并写一条测试把"注入真的改变了行为"钉住。

## 只写字段可能掩盖真 bug：`volume_` → 切轨重置音量

`RendererImpl::volume_` 只写不读，看着像"删掉就完了"。**但它掩盖了一个行为 bug**：

音轨切换时，用户设置是从**即将销毁的音频渲染器**上取的：

```cpp
const SwitchedAudioSettings settings{audio_->volume(), audio_->muted(), ...};
```

`AudioRendererImpl` 自己也从默认值起（1.0 / 1x），只有 `SetVolume` 的 `PostTask`
在 S4 跑过才知道用户设了什么。于是两种情况丢设置：

1. **音频腿存在之前设的音量**：`RendererImpl::SetVolume` 存进 `volume_`，但 `audio_`
   还是 null，没转发 → 切轨读到 1.0。
2. **setter 还排在 S4 队列里**：S1 上的切换先读旧值。

结果都是「切一次音轨，音量悄悄回 1.0」；倍速同形且更响（时钟 2x、音频 1x）。

修法：`volume_` / `playback_rate_` 成为切换的**权威来源**（`volume_` 改
`std::atomic<float>`，因为 `SetVolume` 任意线程可调）。`muted` / `preserves_pitch`
仍从 `audio_` 取 —— 没有渲染器级 setter，`audio_` 是唯一持有者。

**教训**：只写字段先问「谁本该读它」，别先问「能不能删」。这个字段的答案是
"切换路径本该读它"，于是它同时解释了冗余和行为 bug。
（与 `tick_clock_` 相反：那个是"没有人该读"，所以删。）

### 怎么给"增益"造一个可观察点

假音频解码器原先**只输出零样本**（`std::vector<uint8_t>(..., 0)`），所以任何增益都
看不出来。给 `FakeDecoderBehaviour` 加 `audio_sample_value`（默认 0，既有套件不变），
渲染路径按 `muted ? 0 : volume` 缩放样本，于是**一串样本的峰值就是增益**。
这比断言"某个 setter 被调用过"强：它证明值真的走到了输出。
