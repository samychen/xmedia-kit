# 审查报告 — xmedia-kit（2026-10-26）

- 范围：全树 540 个 `.cc`/`.h`（排除 `tools/deps/`、`third_party/`）+ 29 篇文档
- 方法：先读 `.workbuddy/memory/`（其他 agent 的长期约定与教训）确定口径；重建构建树后
  跑门禁取当场实测值；逐条缺陷都回到源码核对并用探针/单测反证
- 原则：只报**可复现**的问题；每条区分「已验证」与「存疑」

## 0. 结论

工程质量本身很高：容器/内存序/错误路径/关闭时序都经得起推敲，注释记录的历史缺陷
（`AddRef` 退化、`PostTaskAndReplyWithResult` 跨序列、`VideoRendererImpl` 析构期 UAF）
确实修对了。这一轮的问题集中在四类：

1. **门禁「绿」是没跑出来的**。三项 CI 风格门禁在实际树上是**红的**，而文档写着
   "全绿"。`check_invariants` 13 条、`clang-format` 100 处、`cpplint` 1 条。
2. **一个文档承诺的功能根本不存在**。`volume` 选项被文档写成"已接通（registry 换算）"，
   实际注册表里没有这个 key，`SetOption` 会报错；而它指向的配置字段
   `audio.startup_volume` 除范围校验外**没有任何读取者**。
3. **一条冗余的公共接口在假装自己是注入点**。`PipelineImpl::SetTickClock()` 只写不读，
   真正的时钟注入走 `SetClock` → `AvSyncController::wall_` → 三个媒体 `Clock`。
   已删（D5），否则下一个读者会照着它去接一条不存在的路径。
4. **一个只写字段掩盖了行为 bug**。`RendererImpl::volume_` 写着却没人读，而音轨切换
   恰好从"即将销毁的音频渲染器"上取用户设置 —— 于是**切一次音轨，用户的音量与倍速
   被重置**（D6）。已修，并在旧代码上验证过测试会红。

## 1. 代码缺陷（已修）

### D1 `volume` 选项不存在，`startup_volume` 是死配置 — 高

| 事实 | 证据 |
|---|---|
| 注册表无 `volume` 条目 | `player/option_registry.cc` 的 9 个 `e.push_back` 里没有它 |
| `SetOption` 会失败 | 探针实测：`SetInt(kPlayer,"volume",80)` → `ok=0 msg=unknown option key` |
| 字段无人读 | 全树 `grep startup_volume` 只命中 `player_config.h`（声明）、`player_config.cc`（范围校验），`player/` 其余零命中 |
| 文档说相反的话 | `docs/MIGRATION.md` §3 表「`volume` 0..100 → 已接通（registry 换算）」；Δ6 也写"registry 对旧字符串 key 做换算" |

修法：
- `player/option_registry.cc` 增加 `volume` 条目（`int 0..100` 与 `double 0..1` 两种入参，
  越界报 `OutOfRange`），换算写进 `audio.startup_volume`。
- `PlayerImpl` 构造函数用 `audio.startup_volume` 播种运行时音量 `volume_`（此前该字段
  永远从 1.0 起）。
- `OnPipelineReady()` 补一次 `ApplyGain()`：`SetVolume()` 在 `PrepareAsync` 之前是
  no-op（`ApplyGain` 拿不到 pipeline 就返回），所以「`SetDataSource` 与 `Prepare` 之间
  设的音量」此前也会被静默丢弃。
- 单测 5 条（`option_registry_unittest.cc` 3 条 + `playback_stats_unittest.cc` 2 条），
  均经**负向验证**：去掉 `volume_.store(...)` 后 `ConfigValueBecomesTheRuntimeVolume` 立刻红。

### D2 C30 把「拿线程 id」误判成「起裸线程」 — 中（门禁误报）

`threading_demo.cc` 3 处被报 `std::thread in an example`，实际是
`std::thread::id`（`Thread::GetThreadId()` 的返回类型）与 `std::vector<std::thread::id>`。
判据应为**创建线程**，不是出现这个词。正则改为 `\bstd::thread\b(?!::)`。

同时 `base/` 那 5 个教学 demo 里有 **5 处真违规**（`std::thread` / `std::vector<std::thread>`），
已全部改成 `base::Thread`（`PostTask` + `WaitableEvent` 确认跑完再 `Stop()`，因为
`Thread::Stop()` 不 drain）。5 个 demo 实跑输出与改前一致（8000 / 消费 5 次 / 400 个
唯一 id / 100 个跨线程任务），证明改写没有改变语义。

### D3 三套 CI 风格门禁实际是红的 — 高（流程）

实测（`tools/gate_local.sh --jobs inv,fmt,lint`，改前）：

| 门禁 | 结果 | 具体 |
|---|---|---|
| `check_invariants` | ❌ 13 条 | C30×8（其中 3 条是 D2 的误报）、C23×5 |
| `clang-format --dry-run --Werror` | ❌ 100 处 / 8 文件 | 集中在 `examples/base/*` 与 `base/memory/ref_counted.h` |
| `cpplint --repository=.` | ❌ 1 条 | `base/logging.cc:49` 用了 `std::move` 但没有 `<utility>` |

修完后三项全绿（`PASS (3): inv fmt lint`），`cpplint` 首次为 0。

> **根因值得记下**：`ref_counted.h` 的 C23 超宽与 clang-format 的违规是同一件事的
> 两面 —— clang-format 按**显示宽度**折中文注释（2 列/字），而 C23 数的是**码点**。
> 所以「clang-format 干净」与「C23 干净」不能互相证明，两边都要跑。
> `base/logging.cc:49` 是 b22a526 引入的，`<utility>` 靠传递包含恰好编过，cpplint
> 抓到的正是这种「编得过但依赖别人 include」的形态。

|---|---|---|---|---|

`tick_clock_` 与 `volume_` 都已处理（D5、D6）；`FFmpegTextDecoder::config_` 未动。

### D5 `SetTickClock` 是冗余的第二条时钟注入路径 — 中（已删）

`PipelineImpl::SetTickClock(const TickClock*)` 存进 `tick_clock_` 后**全树无人读**。
更要紧的是它的存在会误导读者以为"时钟注入走这条路"，而真实路径是：

```
Player::Impl
  deps_->tick_clock ──┬─→ AvSyncController(master, tick_clock, ...)   // wall_
                      │        └─→ Clock audio_/video_/external_ 的 wall_
                      │                 └─→ NowTicks()   ← 真正被调用的地方
                      └─→ X  pipeline->SetTickClock(...)  ← 存了没人读
```

所以时钟注入**一直是生效的**，只是 `PipelineImpl` 那份拷贝纯属冗余 —— 它要求的
"`|clock|` must outlive the pipeline"这条契约也没有任何代码兑现。

处置依据是项目自己的原则（`docs/TODO §2`：注册表条目要么有下游读取者，要么移除，
不保留"接受但不做事"的接口），删掉 5 处：声明、成员、实现，以及
`player_impl_prepare.cc` 与两个测试 fixture 里的调用。`SetClock()` 的注释现在写明
**它就是唯一的时钟注入点**，并说明为什么旁边不该再长出一个 `SetTickClock`。

> 没有反向选择"接上它"：Pipeline 内部根本没有 `NowTicks()` 调用点（媒体时钟在
> `media/filters/legacy/clock.cc`），接上去就得凭空造一个消费者。

### D6 音轨切换会把用户的音量与倍速重置 — 高（已修）

D4 里那个"只写"的 `RendererImpl::volume_` 不只是冗余，它掩盖了一个真 bug：

```cpp
// 切轨时从「即将销毁的音频渲染器」上取用户设置
const SwitchedAudioSettings settings{audio_->volume(), audio_->muted(),
                                     audio_->playback_rate(),
                                     audio_->preserves_pitch()};
```

`AudioRendererImpl` 自己也是从默认值起（`volume_{1.0f}`、`playback_rate_{1.0}`），
只有 `SetVolume` 的 `PostTask` 在 S4 上跑过之后才知道用户设了什么。于是两种情况会丢：

1. **用户在音频腿存在之前设了音量** —— `RendererImpl::SetVolume` 存进 `volume_`，
   但 `audio_` 还是 null，没有转发；切轨时读 `audio_->volume()` 得到 1.0。
2. **setter 还排在 S4 队列里** —— S1 上的切换先读了旧值。

两种情况都是"切一次音轨，音量悄悄变成 1.0"。倍速同形，而且更响：时钟仍在 2x，
音频却回到 1x。

修法：这两个字段成为切换的**权威来源**（`volume_` 改为 `std::atomic<float>`，
因为 `SetVolume` 任意线程可调；`playback_rate_` 本来就只在 S1 读写）。
`muted` 与 `preserves_pitch` 仍从 `audio_` 取 —— 这个构建没有渲染器级的 setter，
`audio_` 是它们唯一的持有者，且必须在它销毁前读。

测试两条（`renderer_multi_source_unittest.cc`）：
- `AVolumeSetBeforeAnyAudioSurvivesTheSwitch` —— **旧代码下必红**（实测峰值 1.0 vs
  期望 ≤0.3），这是覆盖修复的那一条。
- `AnAudioTrackSwitchKeepsTheUsersVolume` —— 基线场景（设值时音频腿已在），新旧代码都绿；
  留着是为了将来"完全不搬运音量"时还有人挡。

> 观察点用了**样本值**而不是 setter 调用：渲染路径按 `muted ? 0 : volume` 缩放样本，
> 所以峰值就是当前增益。为此给 `FakeDecoderBehaviour` 加了 `audio_sample_value`
> （默认 0，保持既有套件逐字节不变）。
>
> 这两条也是 `SwitchAudioRenderer` **首次**被测试覆盖 —— 此前该文件只有"拒绝切换"的用例。
